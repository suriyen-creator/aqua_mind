# AquaMind — 66 คำถาม–คำตอบ เตรียมพรีเซ็นระดับภาค

> ฉบับซ้อมตอบกรรมการ วันที่ 25 กรกฎาคม 2569  
> คำตอบเขียนเป็นภาษาพูด สามารถตอบได้ภายในประมาณ 20–45 วินาทีต่อข้อ

## สิ่งที่ต้องจำก่อนขึ้นเวที

1. เรียกผลปัจจุบันว่า **“ดัชนีเฝ้าระวังสภาพแวดล้อม 0–100”** ห้ามเรียกว่าเปอร์เซ็นต์โอกาสเกิดแพลงก์ตอนบลูม
2. ข้อมูล Weather/Ocean และ Sentinel-2 ที่เข้า MVP เป็นข้อมูลจริง แต่ Target ที่ใช้ฝึก Watch model ปัจจุบันเป็นกฎที่ทีมเปิดเผย ไม่ใช่ Ground truth ภาคสนาม
3. ปัจจุบันมี Verified ground truth **0 แถว** จึงยังไม่อ้างความแม่นยำภาคสนาม และระบบตั้งใจระงับ Operational Bloom probability ไว้
4. ผล 50.5/100 ของบางแสนเป็นผลทดสอบเมื่อวันที่ 17 กรกฎาคม 2569 ไม่ใช่ค่าของวันนี้ ก่อนสาธิตต้องอ่านเวลาอัปเดตจากหน้าจอจริงทุกครั้ง
5. ประโยคปลอดภัยเมื่อไม่แน่ใจคือ  
   **“หลักฐานปัจจุบันยังไม่พอให้สรุปเรื่องนั้นครับ/ค่ะ สิ่งที่เราทำได้แล้วคือ... และขั้นต่อไปจะพิสูจน์ด้วย...”**

## A. ปัญหา แนวคิด และคุณค่าของโครงการ

### 1. AquaMind คืออะไร อธิบายสั้น ๆ ได้ไหม?

**คำตอบ:** AquaMind เป็นแพลตฟอร์มช่วยเฝ้าระวังสภาพแวดล้อมชายฝั่งสำหรับเกษตรกรเพาะเลี้ยงสัตว์น้ำ ระบบรวมข้อมูลอากาศ สมุทรศาสตร์ และภาพดาวเทียม แล้วแสดงดัชนี 0–100 พร้อมบอกปัจจัยที่ดันคะแนนและสิ่งที่ควรตรวจในพื้นที่จริง จุดประสงค์คือช่วยให้ผู้ใช้รู้ว่า “เมื่อไรควรเพิ่มการเฝ้าระวัง” ไม่ใช่ใช้ AI ฟันธงว่าเกิดแพลงก์ตอนบลูมแล้ว

### 2. โครงการนี้แก้ปัญหาอะไร?

**คำตอบ:** ปัญหาคือการเปลี่ยนแปลงของสภาพน้ำเกิดได้รวดเร็ว แต่การตรวจภาคสนามทำได้เป็นบางจุดและมีต้นทุน ขณะที่ข้อมูลหลายแหล่งกระจัดกระจาย AquaMind จึงนำข้อมูลเหล่านั้นมารวมเป็นภาพเดียว เพื่อช่วยจัดลำดับเวลาและพื้นที่ที่ควรตรวจน้ำก่อน

### 3. ใครคือผู้ใช้หลัก?

**คำตอบ:** ผู้ใช้หลักที่ออกแบบไว้คือเกษตรกรเพาะเลี้ยงสัตว์น้ำชายฝั่ง ส่วนผู้ใช้สนับสนุนคือเจ้าหน้าที่ประมง นักวิจัย สหกรณ์ และหน่วยงานท้องถิ่น อย่างไรก็ตาม เรายังต้องสัมภาษณ์แยกให้ชัดว่าใครเป็นผู้ใช้ ใครเป็นผู้ซื้อ ใครเป็นผู้จ่าย และใครเป็นผู้อนุมัติงบ

### 4. ทำไมปัญหาแพลงก์ตอนบลูมจึงสำคัญ?

**คำตอบ:** เมื่อแพลงก์ตอนเพิ่มจำนวนมากหรือสลายตัว ออกซิเจนละลายในน้ำอาจลดลงและกระทบสัตว์น้ำ บางชนิดอาจสร้างสารพิษหรือกระทบเหงือกได้ แต่ความรุนแรงขึ้นกับหลายปัจจัย จึงไม่ควรตัดสินจากสีของน้ำหรือค่าตัวแปรเดียว ระบบของเราจึงเน้นการเฝ้าระวังหลายปัจจัยและการตรวจยืนยัน

### 5. ทำไมต้องเตือนล่วงหน้า 3–5 วัน?

**คำตอบ:** ช่วง 3–5 วันเป็นเป้าหมายที่ทำให้ผู้ใช้ยังมีเวลาตรวจน้ำ เตรียมเครื่องให้อากาศ วางแผนแรงงาน หรือปรึกษาเจ้าหน้าที่ และยังอยู่ในช่วงที่ข้อมูลพยากรณ์อากาศพอใช้ประกอบการตัดสินใจได้ แต่เรายังไม่อ้างว่า Lead time นี้ลดความเสียหายจริง จนกว่าจะทำ Actionability trial กับผู้ใช้

### 6. ชื่อ AquaMind สื่อถึงอะไร?

**คำตอบ:** “Aqua” หมายถึงน้ำ และ “Mind” หมายถึงการคิดและตัดสินใจ ชื่อนี้จึงสื่อถึงระบบที่ช่วยคิดจากข้อมูลสภาพแวดล้อม แต่ยังให้มนุษย์และผู้เชี่ยวชาญเป็นผู้ตัดสินใจขั้นสุดท้าย

### 7. ผลลัพธ์ที่ผู้ใช้ได้รับคืออะไร?

**คำตอบ:** ผู้ใช้เห็นระดับติดตามปกติ เฝ้าระวัง หรือรีบตรวจเพิ่ม พร้อมเวลาของข้อมูลล่าสุด ปัจจัยสำคัญที่มีส่วนต่อคะแนน และรายการสิ่งที่ควรตรวจ เช่น สี กลิ่น พฤติกรรมสัตว์ และค่า DO ระบบไม่ได้ให้แค่ตัวเลข แต่เชื่อมตัวเลขไปสู่ขั้นตอนตรวจสอบที่ทำได้

### 8. ขอบเขตพื้นที่ของโครงการคือที่ใด?

**คำตอบ:** เป้าหมายพื้นที่นำร่องคือชายฝั่งอ่าวไทยตอนบน ตั้งแต่ฉะเชิงเทราถึงชลบุรี ส่วน MVP ปัจจุบันสาธิต 3 สถานีในชลบุรี และมี Sentinel-2 AOI จริงบริเวณนอกชายฝั่งบางแสน เราไม่อ้างว่าผลจากพื้นที่นี้ใช้ได้กับทุกจังหวัดโดยไม่สอบเทียบใหม่

### 9. ความสำเร็จของโครงการวัดจากอะไร?

**คำตอบ:** เราแยกความสำเร็จเป็นสี่ด้าน คือ โมเดลตรวจเหตุได้ดีและสอบเทียบได้ ผู้ใช้เข้าใจและนำ Alert ไปตรวจจริง ระบบทำงานน่าเชื่อถือ และมีผู้จ่ายที่ทำให้ต้นทุนต่อฟาร์มคุ้มค่า ดังนั้นความสำเร็จไม่ใช่แค่โมเดลรันได้หรือ Dashboard สวย

### 10. ต่างจากการดูพยากรณ์อากาศทั่วไปอย่างไร?

**คำตอบ:** พยากรณ์อากาศทั่วไปให้ตัวแปรแยกกัน แต่ AquaMind รวม Weather/Ocean กับหลักฐานดาวเทียมที่ผ่าน QC จัดเป็นระดับเฝ้าระวัง อธิบายปัจจัย และเชื่อมไปยังแนวทางตรวจน้ำ อย่างไรก็ตาม หากการทดสอบจริงพบว่าโมเดลไม่ดีกว่า Weather-only baseline เราจะลดขอบเขต ไม่อ้างว่า AI เพิ่มคุณค่า

### 11. ทำไมโครงการนี้จึงสอดคล้องกับ SDG 14?

**คำตอบ:** SDG 14 เน้นการอนุรักษ์และใช้ทรัพยากรทางทะเลอย่างยั่งยืน AquaMind สนับสนุนเป้าหมายนี้ด้วยการช่วยติดตามสภาพแวดล้อมชายฝั่งและลดการตัดสินใจที่ล่าช้า แต่ผลกระทบต่อ SDG จะอ้างได้เต็มที่เมื่อเราวัดผลจริง เช่น เวลาที่ตรวจพบเร็วขึ้นหรือความเสียหายที่หลีกเลี่ยงได้

## B. ข้อมูล เทคโนโลยี และการทำงานของระบบ

### 12. ระบบทำงานตั้งแต่ต้นจนจบอย่างไร?

**คำตอบ:** ระบบดึง Weather/Ocean forecast ตามพิกัด และค้นภาพ Sentinel-2 ของพื้นที่ จากนั้นตรวจคุณภาพ คำนวณ Feature แล้วส่งเข้า XGBoost เพื่อสร้าง Watch index ใช้ SHAP อธิบายปัจจัย และใช้ Rule layer แปลงระดับคะแนนเป็นแนวทางตรวจสอบ ก่อนส่งผ่าน FastAPI ไปยังหน้าเว็บ Next.js และ Streamlit

### 13. ใช้ข้อมูลอะไรบ้าง?

**คำตอบ:** ข้อมูลหลักคืออุณหภูมิอากาศ ฝน เมฆ ลม อุณหภูมิผิวน้ำทะเล คลื่น กระแสน้ำ และระดับน้ำจาก Weather/Ocean API ข้อมูลรองคือ Sentinel-2 L2A ซึ่งใช้แถบแสงเพื่อคำนวณ NDCI และ NDWI ในอนาคตจะเพิ่ม Ground truth ที่มีวัน เวลา พิกัด และวิธีตรวจที่ชัดเจน

### 14. ทำไมเลือก Sentinel-2?

**คำตอบ:** Sentinel-2 เป็นข้อมูลเปิด มีแถบคลื่นที่เหมาะกับการคำนวณดัชนีสีของน้ำ และมีความละเอียดประมาณ 10–20 เมตร จึงเหมาะกับการสร้างต้นแบบชายฝั่งมากกว่าข้อมูลระดับภูมิภาคที่หยาบมาก แต่ยังมีข้อจำกัดเรื่องเมฆ รอบการถ่าย และสัญญาณรบกวนบริเวณน้ำตื้น

### 15. NDCI คืออะไร?

**คำตอบ:** NDCI เป็นดัชนีจากแถบ Red-edge และ Red ที่ใช้ดูความเปลี่ยนแปลงของสัญญาณสีซึ่งอาจสัมพันธ์กับคลอโรฟิลล์ แต่ NDCI สูงไม่ได้แปลว่าเป็นแพลงก์ตอนพิษแน่นอน เพราะได้รับผลจากตะกอน ความขุ่น แสง และชนิดของน้ำด้วย เราจึงใช้เป็นหลักฐานรองและต้องตรวจภาคสนามยืนยัน

### 16. NDWI คืออะไร และใช้ทำไม?

**คำตอบ:** NDWI เป็นดัชนีที่ช่วยแยกหรือยืนยันบริเวณน้ำจากข้อมูลภาพถ่ายดาวเทียม ในระบบนี้ใช้ประกอบการตรวจพื้นที่น้ำและคุณภาพข้อมูล ไม่ใช่ตัวชี้ขาดว่าเกิด Bloom

### 17. ทำไมเลือก XGBoost?

**คำตอบ:** XGBoost เหมาะกับข้อมูลตารางหลายตัวแปร ทำงานได้ดีโดยไม่ต้องใช้ GPU และรองรับการอธิบายด้วย SHAP ได้สะดวก สำหรับ MVP เราใช้ XGBoost regression เรียนเลียนแบบกฎดัชนีที่เปิดเผย เพื่อพิสูจน์เส้นทางข้อมูลและการอธิบายผลก่อนมี Ground truth เพียงพอ

### 18. ทำไมไม่ใช้ Deep Learning?

**คำตอบ:** ตอนนี้ข้อมูลภาคสนามที่ยืนยันแล้วยังไม่มี การใช้โมเดลซับซ้อนกว่าจะเพิ่มความเสี่ยงต่อการจำข้อมูลและอธิบายยากโดยไม่ได้เพิ่มหลักฐานว่าแม่นกว่า XGBoost เราเลือกโมเดลให้เหมาะกับปริมาณข้อมูล และจะเปรียบเทียบกับ Baseline ก่อนเพิ่มความซับซ้อน

### 19. SHAP คืออะไร?

**คำตอบ:** SHAP ช่วยแสดงว่า Feature ใดมีส่วนดันคะแนนขึ้นหรือลงในผลรอบนั้น สำหรับ MVP ค่า SHAP อยู่ในหน่วย “จุดของ Watch index” ไม่ใช่เปอร์เซ็นต์ความเสี่ยง และไม่ใช่หลักฐานเชิงเหตุและผลทางชีววิทยา

### 20. ข้อมูลในระบบเป็นข้อมูลจริงหรือข้อมูลจำลอง?

**คำตอบ:** หน้า Live ใช้ Weather/Ocean จริง และบางแสนใช้ Sentinel-2 จริงเมื่อผ่าน QC แต่ Target ของ Watch model ปัจจุบันสร้างจากกฎที่ทีมกำหนดและเปิดเผย ส่วนข้อมูลจำลองใช้สำหรับทดสอบเส้นทาง Model–API–Dashboard เท่านั้น เราแสดงสถานะข้อมูลเพื่อไม่ให้ผู้ใช้สับสนสองส่วนนี้

### 21. แล้วทำไมต้องเริ่มจากข้อมูลจำลอง?

**คำตอบ:** ข้อมูลจำลองช่วยให้เราพัฒนาและทดสอบโครงสร้างระบบครบวงจรได้ก่อน เช่น Schema, API, Dashboard และ Error handling โดยไม่หลอกว่าเป็นหลักฐานความแม่นยำ ขั้นต่อมาจึงเชื่อม Input จริง และขั้นพิสูจน์สุดท้ายต้องใช้ Ground truth จริง

### 22. คะแนน 0–100 คำนวณอย่างไร?

**คำตอบ:** กฎปัจจุบันมีคะแนนฐานและ Weather/Ocean รวมไม่เกิน 80 จุด และ Sentinel-2 ที่ผ่านเกณฑ์เพิ่มได้ไม่เกิน 20 จุด จากนั้น XGBoost เรียนเลียนแบบกฎนี้ ค่าเฉลี่ยความคลาดเคลื่อนจากกฎอยู่ประมาณ 0.54 จุด แต่ตัวเลขนี้วัดการเลียนแบบกฎ ไม่ใช่ความแม่นยำในการทำนาย Bloom

### 23. ระดับคะแนนแบ่งอย่างไร?

**คำตอบ:** ต่ำกว่า 50 คือ “ติดตามปกติ” 50–69 คือ “เฝ้าระวัง” และ 70–100 คือ “รีบตรวจเพิ่ม” ระดับเหล่านี้เป็นกฎสื่อสารของ Watch index ปัจจุบัน ไม่ใช่เกณฑ์ทางชีววิทยาที่ยืนยัน Bloom และต้องปรับจากผล Validation กับผู้ใช้ในอนาคต

### 24. ถ้าไม่มีภาพดาวเทียม ระบบทำอย่างไร?

**คำตอบ:** Watch index ปัจจุบันยังทำงานจาก Weather/Ocean ซึ่งเป็นข้อมูลหลัก แต่ระบบลดความครบถ้วนของหลักฐานและบอกผู้ใช้ว่าไม่มีภาพใหม่ สำหรับ Operational model ในอนาคต เราจะฝึก No-image model แยก และถ้าไม่ผ่านเกณฑ์ตามอายุข้อมูลจะไม่แสดง Probability

### 25. ถ้ามีเมฆมาก ภาพยังใช้ได้อย่างไร?

**คำตอบ:** เราไม่ดูแค่เปอร์เซ็นต์เมฆทั้ง Scene เพราะ AOI ขนาดเล็กอาจยังมีพิกเซลน้ำที่ใช้ได้ ระบบจึงใช้ SCL water mask และดู Local valid-pixel ratio ด้วย ตัวอย่างวันที่ 14 กรกฎาคม Scene cloud 75.448% แต่ AOI บางแสนมี valid water pixel ratio 1.00 จึงผ่าน QC เฉพาะพื้นที่

### 26. ความละเอียด 20 เมตรเพียงพอถึงระดับกระชังหรือไม่?

**คำตอบ:** ไม่ควรอ้างว่าแยกกระชังเดี่ยวได้ทุกขนาด ความละเอียด 20 เมตรเหมาะกับการดูบริเวณหรือแนวโน้มรอบฟาร์มมากกว่า และข้อมูล Weather/Ocean ยังเป็นกริดที่หยาบกว่า เราจึงออกแบบเป็นเครื่องมือจัดลำดับการตรวจ ไม่ใช่เซนเซอร์ประจำกระชัง

### 27. ป้องกันการใช้ข้อมูลอนาคตในการฝึกอย่างไร?

**คำตอบ:** ทุกตัวอย่างยึด issue time เป็นเวลาตัดสินใจ ภาพดาวเทียมต้องเกิดก่อนเวลานั้นและเผื่อ processing latency 8 ชั่วโมง ส่วน Weather ต้องมาจาก forecast run ที่ออกก่อน issue time เราแบ่งข้อมูลตามเวลาและพื้นที่ เพื่อไม่ให้ข้อมูลอนาคตหรือเหตุการณ์เดียวกันรั่วข้ามชุด

### 28. สถาปัตยกรรมระบบประกอบด้วยอะไรบ้าง?

**คำตอบ:** Backend ใช้ Python และ FastAPI สำหรับ Pipeline, Model และ API หน้าแสดงผลมี Next.js และ Streamlit ข้อมูลภาพประมวลผลจาก Sentinel-2 ผ่าน Earth Search ส่วน XGBoost และ SHAP ใช้คำนวณคะแนนและคำอธิบาย สถาปัตยกรรมเป้าหมายจะเพิ่มฐานข้อมูล การแจ้งเตือน Registry, Monitoring และ Security

### 29. ถ้า API หรือผู้ให้บริการข้อมูลล่มจะเกิดอะไรขึ้น?

**คำตอบ:** หลักการของเราคือ Fail closed คือแสดงว่า Degraded หรือ Unavailable พร้อมเวลาที่ข้อมูลดีครั้งสุดท้าย และไม่ใช้สีเขียวแทนคำว่า “ไม่มีข้อมูล” ปัจจุบันมี Error/Retry และ Snapshot fallback บางส่วน แต่ระบบแจ้งเตือนสำรองและ Incident runbook ยังเป็นงานก่อน Production

### 30. ทีมพัฒนาอะไรเองบ้าง?

**คำตอบ:** ทีมพัฒนา Data flow, Feature pipeline, Watch rule, XGBoost service, SHAP ภาษาชาวบ้าน, Assessment gate, FastAPI, Dashboard และ Farmer Response Protocol เอง ส่วน Framework และข้อมูลดาวเทียมเป็นเทคโนโลยีเปิดที่นำมาใช้อย่างระบุแหล่งที่มา

### 31. ระบบผ่านการทดสอบอะไรแล้ว?

**คำตอบ:** หลักฐานในรายงานล่าสุดระบุว่า Backend ผ่าน 11 tests, Streamlit AppTest ผ่าน และ Frontend ผ่าน ESLint กับ Production build การทดสอบเหล่านี้ยืนยันการทำงานของซอฟต์แวร์ระดับ MVP แต่ไม่ใช่การยืนยันความแม่นยำภาคสนามของโมเดล

### 32. ทำไมมีทั้ง Next.js และ Streamlit?

**คำตอบ:** Streamlit ช่วยให้เผยแพร่และสาธิต Live watch ได้รวดเร็ว ส่วน Next.js ใช้พัฒนา Dashboard ที่ควบคุมประสบการณ์ผู้ใช้และต่อยอด Production ได้มากกว่า ทั้งสองหน้าใช้แนวคิดผลลัพธ์เดียวกัน และ Backend เป็นแหล่งตรรกะหลักเพื่อลดความไม่สอดคล้อง

### 33. ตัวเลข 50.5 ของบางแสนหมายถึงอะไร?

**คำตอบ:** หมายถึง Watch index 50.5 จาก 100 ในการทดสอบวันที่ 17 กรกฎาคม 2569 จัดอยู่ระดับ “เฝ้าระวัง” ไม่ใช่โอกาสเกิด Bloom 50.5% และไม่ควรใช้แทนค่าปัจจุบันของวันนี้โดยไม่ดู timestamp บนหน้าจอ

## C. โมเดล ความแม่นยำ และคำถามเชิงวิทยาศาสตร์

### 34. โมเดลแม่นยำกี่เปอร์เซ็นต์?

**คำตอบ:** ตอนนี้เรายังตอบเป็นเปอร์เซ็นต์ความแม่นยำภาคสนามไม่ได้ เพราะ Verified ground truth มี 0 แถว สิ่งที่ยืนยันได้คือซอฟต์แวร์และ Pipeline ทำงาน และ Watch model เลียนแบบกฎได้คลาดเคลื่อนเฉลี่ยประมาณ 0.54 จุด การอ้าง Accuracy ต้องรอ Independent test events จริง

### 35. ถ้ายังไม่มี Ground truth ทำไมเรียกว่า AI?

**คำตอบ:** ระบบมี Machine Learning จริง เพราะใช้ XGBoost และ SHAP แต่ในสถานะปัจจุบัน AI ทำหน้าที่เป็น rule surrogate สำหรับดัชนีเฝ้าระวัง ไม่ใช่โมเดลยืนยัน Bloom เราตั้งชื่อ Output และใส่ Approval gate ให้ตรงกับระดับหลักฐาน เพื่อไม่ให้คำว่า AI สร้างความมั่นใจเกินจริง

### 36. ถ้ายังทำนาย Bloom ไม่ได้ โครงการมีคุณค่าตรงไหน?

**คำตอบ:** คุณค่าปัจจุบันคือการรวมข้อมูลจริงหลายแหล่ง แสดงความสดใหม่ อธิบายปัจจัย และช่วยจัดลำดับว่าควรตรวจน้ำเมื่อไร ส่วนคุณค่าการพยากรณ์ Bloom เป็นสมมติฐานขั้นต่อไปที่ต้องพิสูจน์ หากโมเดลไม่ผ่าน เราก็ยังใช้ระบบเป็นเครื่องมือ Environmental watch หรือจัดลำดับการลงพื้นที่ได้โดยไม่โอเวอร์เคลม

### 37. จะเก็บ Ground truth อย่างไร?

**คำตอบ:** หนึ่งแถวต้องมีวันเวลา พิกัด สถานะ Bloom วิธีตรวจ และสถานะการยืนยัน เช่น microscopy, cell count หรือ laboratory chlorophyll-a เฉพาะข้อมูล `VERIFIED` จึงเข้าชุดฝึก และการไม่มีรายงานจะไม่ถูกนับเป็น Negative อัตโนมัติ

### 38. นิยาม Label สำหรับการเตือนล่วงหน้าอย่างไร?

**คำตอบ:** ตัวอย่างหนึ่งแถวคือการตัดสินใจ ณ เวลา t และ Label คือผลตรวจที่ยืนยันแล้วในช่วง t+3 ถึง t+5 วัน หากไม่มีการตรวจในช่วงนั้นจะตัดตัวอย่างออก ไม่ตีความว่าไม่เกิดเหตุ วิธีนี้ทำให้เราวัด Early warning จริง ไม่ใช่นำค่าปัจจุบันมาทำนายตัวเอง

### 39. จะแบ่ง Train, Validation และ Test อย่างไร?

**คำตอบ:** แบ่งตามเวลา 60/20/20 และกันพื้นที่หรือ event group เพื่อไม่ให้เหตุการณ์เดียวกันรั่วข้ามชุด ชุด Validation ใช้เลือก Threshold และ Calibration ส่วน Test ใช้ประเมินครั้งสุดท้าย และควรกันเหตุการณ์อิสระอย่างน้อยหนึ่งช่วงเมื่อมีข้อมูลเพียงพอ

### 40. ทำไมไม่ใช้ Accuracy เป็นตัวชี้วัดหลัก?

**คำตอบ:** Bloom เป็นเหตุการณ์ที่อาจเกิดไม่บ่อย โมเดลที่ทายว่า “ไม่เกิด” ตลอดอาจมี Accuracy สูงแต่ไม่มีประโยชน์ เราจึงดู Recall, Precision, F1, PR-AUC, False alarms และ Calibration พร้อมช่วงความเชื่อมั่น

### 41. Recall และ Precision ต่างกันอย่างไร?

**คำตอบ:** Recall ตอบว่าในเหตุการณ์จริงทั้งหมด เราเตือนได้กี่เหตุการณ์ ส่วน Precision ตอบว่าใน Alert ทั้งหมด มีกี่ครั้งที่เกิดเหตุจริง Recall ต่ำเสี่ยงพลาดเหตุ แต่ Precision ต่ำทำให้เตือนเกินและผู้ใช้เสียต้นทุน จึงต้องเลือกสมดุลร่วมกับผู้ใช้

### 42. เป้าหมายความแม่นยำของโครงการคือเท่าไร?

**คำตอบ:** เป้าหมายในรายงานคือ Recall อย่างน้อย 80% และ Precision อย่างน้อย 60% บน Independent test set พร้อม Brier Score ดีกว่า Baseline ส่วน Gate ขั้นต่ำในโค้ดปัจจุบันคือ Recall 70%, Precision 50%, Brier ไม่เกิน 0.25 เราจะใช้เป้าหมายรายงานที่เข้มกว่าเป็นเกณฑ์กล่าวอ้าง และทบทวนตามต้นทุนจริงของการเตือนผิด

### 43. False Negative กับ False Positive อย่างไหนร้ายแรงกว่า?

**คำตอบ:** False Negative อาจทำให้พลาดการเตรียมรับมือและเกิดความเสียหาย ส่วน False Positive ทำให้เสียค่าแรง ค่าตรวจ หรือเกิด Alert fatigue เราจึงไม่ตอบว่าอย่างใดสำคัญกว่าโดยไม่มีข้อมูลต้นทุน แต่จะเก็บ Cost matrix กับเกษตรกรและเจ้าหน้าที่แล้วเลือก Threshold จากผลกระทบจริง

### 44. Calibration คืออะไร และสำคัญอย่างไร?

**คำตอบ:** Calibration ตรวจว่าค่าความน่าจะเป็นที่โมเดลรายงานสอดคล้องกับความถี่จริงหรือไม่ เช่น ถ้าระบบบอก 70% หลายครั้ง เหตุควรเกิดใกล้ 70% ของครั้งเหล่านั้น เรื่องนี้ใช้กับ Operational probability ในอนาคต ไม่ใช่ Watch index ปัจจุบัน

### 45. Brier Score คืออะไร?

**คำตอบ:** Brier Score วัดความคลาดเคลื่อนของค่าความน่าจะเป็น ยิ่งต่ำยิ่งดี และลงโทษการทำนายที่มั่นใจแต่ผิด เราจะใช้ร่วมกับ Calibration curve และไม่ดูแค่การแบ่งถูกหรือผิด

### 46. ทำไมต้องใช้ SMOTE?

**คำตอบ:** SMOTE เป็นหนึ่งในวิธีทดลองรับมือข้อมูลเหตุการณ์ที่ไม่สมดุล โดยสร้างตัวอย่างสังเคราะห์เฉพาะใน Training fold เท่านั้น เราจะเปรียบเทียบกับ Class weight และเลือกจาก Validation ไม่สรุปล่วงหน้าว่า SMOTE ต้องดีกว่า

### 47. จะเปรียบเทียบโมเดลกับอะไร?

**คำตอบ:** เราจะเทียบกับ Majority class, กฎ NDCI threshold, Logistic regression, Weather-only model, Satellite-only model และ Full model ถ้าโมเดลซับซ้อนไม่ดีกว่า Baseline อย่างมีนัยสำคัญ เราจะไม่ใช้ความซับซ้อนนั้น

### 48. ต้องมีข้อมูลอย่างน้อยกี่แถว?

**คำตอบ:** Gate ปัจจุบันกำหนดขั้นต่ำ 100 verified rows และอย่างน้อย 10 positive events ในชุดทดสอบ แต่ตัวเลขนี้เป็นเพียงขั้นต่ำสำหรับไม่ให้ Pipeline เปิดโมเดลง่ายเกินไป ไม่ใช่หลักฐานว่าข้อมูลเพียงพอทางสถิติ แผนจริงต้องคำนวณ sample size และเก็บหลายเหตุการณ์ หลายฤดูกาล

### 49. ถ้าไม่มีภาพดาวเทียม ความแม่นยำจะลดลงเท่าไร?

**คำตอบ:** ตอนนี้ยังไม่มีหลักฐานพอที่จะตอบเป็นตัวเลข เราจะฝึก Full model และ No-image model แยกกัน แล้วรายงาน Recall, Precision และ Calibration ตามช่วงอายุภาพ 0–5, 6–10 และมากกว่า 10 วัน ถ้า bucket ใดไม่ผ่านจะงดแสดง Probability

### 50. SHAP พิสูจน์สาเหตุของ Bloom ได้หรือไม่?

**คำตอบ:** ไม่ได้ SHAP อธิบายว่า Feature ใดมีส่วนต่อผลของโมเดลในรอบนั้น แต่ไม่ได้พิสูจน์ว่าปัจจัยนั้นเป็นสาเหตุทางชีววิทยา เราจึงใช้คำว่า “มีส่วนดันคะแนน” ไม่ใช้คำว่า “ทำให้เกิด Bloom”

### 51. NDCI บอกชนิดหรือพิษของแพลงก์ตอนได้ไหม?

**คำตอบ:** ไม่ได้ NDCI เป็นสัญญาณเชิงแสงที่อาจสัมพันธ์กับคลอโรฟิลล์ แต่ไม่สามารถยืนยันชนิด ความหนาแน่น หรือสารพิษได้ การยืนยันต้องใช้การเก็บตัวอย่าง กล้องจุลทรรศน์ การนับเซลล์ หรือการตรวจทางห้องปฏิบัติการที่เหมาะสม

### 52. ภาพล่าสุดอาจเก่า แล้วระบบยังน่าเชื่อถือหรือไม่?

**คำตอบ:** ระบบต้องแสดงอายุภาพทุกครั้งและไม่เรียกข้อมูลเก่าว่า Real-time สำหรับ Watch index ภาพเป็นหลักฐานรองและถูกตัดออกเมื่อเกินเกณฑ์ ส่วน Operational probability จะต้องผ่าน Validation แยกตามอายุภาพ มิฉะนั้นระบบจะแสดงว่า “ข้อมูลไม่เพียงพอ”

### 53. เหตุใดจึงเลือก Weather-first?

**คำตอบ:** เพราะ Weather/Ocean มีรอบอัปเดตสม่ำเสมอกว่าภาพดาวเทียม และช่วยให้ระบบไม่หยุดทำงานทันทีเมื่อมีเมฆ แต่ข้อมูลเหล่านี้เป็นสภาวะเอื้อในกริดระดับภูมิภาค ไม่ใช่หลักฐาน Bloom ระดับฟาร์ม จึงต้องใช้ภาษาและการแสดงผลอย่างระมัดระวัง

## D. การใช้งานจริง ผลกระทบ และความปลอดภัย

### 54. เมื่อระบบขึ้นระดับเฝ้าระวัง เกษตรกรควรทำอะไร?

**คำตอบ:** ควรเพิ่มความถี่การสังเกตสีและกลิ่นน้ำ ดูพฤติกรรมสัตว์ วัด DO หากมีอุปกรณ์ และเตรียมช่องทางติดต่อผู้เชี่ยวชาญ การดำเนินการที่มีต้นทุนสูงควรรอผลตรวจพื้นที่จริง ไม่ทำจากคะแนน AI เพียงอย่างเดียว

### 55. เมื่อระบบขึ้นระดับรีบตรวจเพิ่ม ควรทำอะไร?

**คำตอบ:** ให้ตรวจ DO, pH, อุณหภูมิ และความเค็มโดยเร็ว โดยเฉพาะบริเวณน้ำนิ่งหรือมุมอับ หากพบสัตว์ลอยหัว กลิ่นหรือสีน้ำผิดปกติให้ติดต่อผู้เชี่ยวชาญ ระบบไม่ควรสั่งเปลี่ยนน้ำ ย้ายกระชัง หรือจับก่อนกำหนดโดยไม่มีข้อมูลพื้นที่จริง

### 56. คำแนะนำของระบบอาจทำให้เกิดอันตรายหรือไม่?

**คำตอบ:** มีความเสี่ยงถ้าผู้ใช้ตีความคะแนนเป็นคำสั่ง เช่น เปลี่ยนน้ำทั้งที่น้ำภายนอกแย่กว่า เราจึงจำกัดคำแนะนำเป็นขั้นตอนตรวจยืนยัน แสดงข้อจำกัด และกำหนดว่าก่อน Production ต้องมี Expert-approved protocol, Escalation และ Audit trail

### 57. โครงการลดความเสียหายได้จริงเท่าไร?

**คำตอบ:** ตอนนี้ยังไม่มี Outcome study จึงยังระบุตัวเลขไม่ได้ สิ่งที่เราจะวัดคือ Actionable lead time, อัตราที่ Alert นำไปสู่การตรวจ, เวลาหรือต้นทุนที่ประหยัด และความเสียหายที่หลีกเลี่ยงได้ โดยใช้กลุ่มเปรียบเทียบเมื่อเหมาะสม

### 58. ลดต้นทุนได้มากกว่า 10 เท่าจริงหรือไม่?

**คำตอบ:** ตัวเลขดังกล่าวเป็นสมมติฐานจากการเทียบค่า Cloud เบื้องต้นกับค่าลงพื้นที่บางกรณี ยังไม่รวมภาคสนาม ห้องแล็บ การเดินทาง การแจ้งเตือน Support, Security และ Compliance ดังนั้นบนเวทีควรเรียกว่า “สมมติฐานต้นทุนที่ต้องพิสูจน์” ไม่ใช่ผลประหยัดที่ยืนยันแล้ว

### 59. ทดสอบกับผู้ใช้จริงแล้วหรือยัง?

**คำตอบ:** การทดสอบ SUS กับผู้ใช้เป้าหมาย 30 รายยังไม่ดำเนินการ จึงยังไม่อ้างคะแนนความพึงพอใจหรือ Product–market fit ขั้นต่อไปคือทดสอบ Task completion และความเข้าใจว่า Forecast ไม่ใช่คำยืนยัน 100% ควบคู่กับ SUS

### 60. ถ้าเกษตรกรไม่มีเครื่องวัดคุณภาพน้ำ ระบบยังมีประโยชน์ไหม?

**คำตอบ:** ยังช่วยบอกช่วงเวลาที่ควรสังเกตน้ำหรือประสานเจ้าหน้าที่ได้ แต่ความสามารถในการตอบสนองจะลดลง นี่เป็นเหตุผลที่ Pilot ต้องสำรวจอุปกรณ์ แรงงาน และช่องทางช่วยเหลือจริง ไม่สมมติว่าทุกคนทำตาม Alert ได้เหมือนกัน

### 61. ผู้สูงอายุหรือผู้ไม่ถนัดเทคโนโลยีจะใช้ได้อย่างไร?

**คำตอบ:** หน้าแสดงผลควรใช้ภาษาไทยง่าย สีพร้อมข้อความ ไม่พึ่งกราฟซับซ้อน และให้ขั้นตอนถัดไปที่ชัดเจน ใน Pilot เราจะทดสอบการใช้งานจริงและอาจใช้ LINE, SMS หรือเจ้าหน้าที่สหกรณ์เป็นช่องทางเสริม แต่ช่องทางแจ้งเตือนจริงยังไม่ได้เชื่อมใน MVP

### 62. จะป้องกันไม่ให้ผู้ใช้เชื่อ AI มากเกินไปอย่างไร?

**คำตอบ:** เราแสดงเวลาข้อมูล สถานะภาพ หลักฐานที่ขาด และข้อความว่าไม่ใช่การยืนยัน Bloom พร้อมใช้ชื่อ “Watch index” แทน “Probability” นอกจากนี้จะทดสอบความเข้าใจของผู้ใช้ ไม่ใช้ความพึงพอใจอย่างเดียวเป็นหลักฐานว่าหน้าจอปลอดภัย

### 63. ข้อมูลพิกัดฟาร์มและข้อมูลผู้ใช้ปลอดภัยหรือไม่?

**คำตอบ:** MVP ยังไม่มี Authentication และ Production database จึงยังไม่ควรเก็บข้อมูลอ่อนไหวของผู้ใช้จริง ก่อน Pilot ต้องเพิ่มการยินยอม การจำกัดสิทธิ์ การเข้ารหัส นโยบายเก็บและลบข้อมูล Audit log และ Threat model ตามหลัก PDPA และ Security review

### 64. ใครรับผิดชอบถ้าระบบเตือนผิด?

**คำตอบ:** ระบบเป็น Decision support ไม่ใช่ผู้สั่งการ แต่ Disclaimer อย่างเดียวไม่เพียงพอ ก่อนใช้จริงต้องกำหนดเจ้าของ Alert ผู้อนุมัติ Protocol ช่องทาง Escalation และเก็บประวัติข้อมูลกับรุ่นโมเดลทุกครั้ง การตัดสินใจที่มีต้นทุนสูงต้องมีมนุษย์หรือผู้เชี่ยวชาญร่วมยืนยัน

## E. ธุรกิจ การขยายผล และความยั่งยืน

### 65. ใครจะเป็นคนจ่ายเงินให้ระบบนี้?

**คำตอบ:** ตอนนี้ยังไม่ควรฟันธง ผู้ใช้อาจเป็นเกษตรกร แต่ผู้จ่ายอาจเป็นสหกรณ์ ฟาร์มขนาดใหญ่ หน่วยงานท้องถิ่น หรือหน่วยงานรัฐ เราจะทำ Customer discovery แยก User, Buyer, Payer และ Approver แล้วใช้ Paid pilot หรือหลักฐานงบประมาณทดสอบจริง

### 66. ทำไมโครงการนี้ควรผ่านระดับภาค และถ้าได้รับโอกาสจะทำอะไรต่อ?

**คำตอบ:** จุดแข็งของ AquaMind ไม่ใช่การอ้างว่า AI แม่นแล้ว แต่คือการสร้าง Vertical slice จากข้อมูลจริงถึงหน้าจอ พร้อมกลไกไม่แสดงผลเกินหลักฐาน ขั้นต่อไปที่ชัดเจนคือเก็บ Verified ground truth หลายเหตุการณ์และหลายฤดูกาล ทำ Independent validation และ Calibration ทดสอบการใช้งานกับเกษตรกร 30 ราย และทำ Shadow pilot กับหน่วยงานพื้นที่ก่อนเปิด Alert จริง การสนับสนุนระดับภาคจะเปลี่ยนต้นแบบที่โปร่งใสให้เป็นระบบที่พิสูจน์ผลกระทบได้

## คำตอบสำรองสำหรับคำถามธุรกิจต่อเนื่อง

หัวข้อนี้ไม่นับเพิ่มจาก 66 ข้อ ใช้ต่อยอดเมื่อกรรมการถามลึกจากข้อ 65–66

### รูปแบบรายได้คืออะไร?

ยังไม่เลือกโมเดลรายได้ก่อนรู้ว่าใครเป็นผู้จ่าย ทางเลือกที่สมเหตุผลกว่าการเก็บรายเดือนจากเกษตรกรทันทีคือ Institutional pilot สำหรับสหกรณ์หรือหน่วยงาน โดยคิดค่าบริการตามพื้นที่หรือจำนวนฟาร์ม หลังจากพิสูจน์ Multi-season validation และต้นทุนจริงแล้วจึงตัดสินใจรูปแบบถาวร

### ต้นทุนระบบมีอะไรบ้าง?

ต้องรวมค่าเก็บตัวอย่าง ห้องแล็บ เรือและการเดินทาง Cloud storage และการประมวลผล Raster ค่าข้อความ Support, Training, Security, Compliance และ Incident response เราจะคำนวณ Cost per farm/month, per monitored km² และ per alert ในกรณี Best, Base และ Worst

### ขยายไปจังหวัดอื่นได้หรือไม่?

ขยายเชิงซอฟต์แวร์ได้เพราะ Pipeline รับพิกัดและเปลี่ยน AOI ได้ แต่ขยายเชิงวิทยาศาสตร์ไม่ได้ด้วยการคัดลอก Threshold เดิมทันที ต้องตรวจชนิดน้ำ ฤดูกาล แหล่งมลพิษ ลักษณะชายฝั่ง และ Ground truth ของพื้นที่ใหม่ รวมทั้งแสดงเมื่อพื้นที่อยู่นอกขอบเขตข้อมูลฝึก

### ถ้าผู้ให้บริการข้อมูลหยุดให้บริการจะทำอย่างไร?

ระบบเป้าหมายใช้ Adapter แยกผู้ให้บริการ และต้องมีทะเบียน Quota, ราคา, License, SLA และแหล่งทดแทน ข้อมูลที่อนุญาตจะถูก Cache พร้อม Lineage หากข้อมูลหลักไม่พร้อม ระบบต้องแสดง Unavailable ไม่สร้างข้อมูลเทียมมาเป็นสถานะปกติ

### คู่แข่งของ AquaMind คือใคร?

คู่แข่งไม่ใช่แค่ Dashboard ดาวเทียม แต่รวมถึงการดูน้ำด้วยประสบการณ์ เซนเซอร์ DO กลุ่ม LINE เจ้าหน้าที่ และบริการข้อมูลภาครัฐ AquaMind ต้องพิสูจน์ว่าช่วยรวมข้อมูล จัดลำดับการตรวจ หรือเพิ่ม Lead time ได้ดีกว่าทางเลือกเหล่านี้ในต้นทุนที่ยอมรับได้

### จุดอ่อนที่สุดของโครงการตอนนี้คืออะไร?

จุดอ่อนที่สุดคือยังไม่มี Verified ground truth จึงยังพิสูจน์การพยากรณ์ Bloom และความแม่นยำภาคสนามไม่ได้ จุดแข็งคือระบบรับรู้ข้อจำกัดนี้และมี Assessment gate ปิด Operational probability ไว้ แผนใช้ทรัพยากรลำดับแรกจึงต้องเป็นการสร้างข้อมูลภาคสนามคุณภาพ ไม่ใช่เพิ่มความซับซ้อนของโมเดล
